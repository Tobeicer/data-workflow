# 游艺圈核心：数据引擎

## 行业参照

1. 微信小程序：游博汇。游博汇当前实现度极低且停止维护，仅做部分参考。
2. 漫立方配件城（行业较大的配件商城），通过邀请入驻获取数据 API，其分类作为直接参考。

## 数据来源策略

### 大平台爬虫

针对 1688、淘宝、拼多多、京东、抖音、闲鱼等大平台，通过爬虫全面采集游戏游艺设备、配件及耗材的商品数据，建立完整商品信息库，覆盖所有可见参数、图片、规格、价格、SKU 和供货状态，支持搜索、比较、询价、推荐和行情分析。

采集范围：1688、淘宝、闲鱼、拼多多、京东、抖音。

### 行业店铺入驻

针对漫立方等垂直行业店铺，通过邀请入驻游艺圈平台获取其数据 API，直接同步商品数据。非爬虫采集。

## 大平台数据范围

游艺圈定位为全网同类商品搬运库，以存储 1688、淘宝、闲鱼、拼多多、京东、抖音等大平台全量商品为目标。大平台数据通过爬虫采集，经 L0-L2 去重、质量和复核处理后形成 L3；平台校验、审核并写入正式业务表，数据侧不绕过平台契约直接写正式产品库。

## 多平台独立采集与字段融合

- 每个平台使用独立采集适配器和来源工作流，分别处理登录、验证码、类目、分页、商品、店铺、公司、资质和平台特有字段。
- n8n 只共享触发、状态、锁、重试、质量、人工门禁、告警和交付契约，不把各平台爬虫强行合并成一套解析脚本。
- 数据层采用“公共核心字段 + 类型化属性事实 + 原始全字段”。平台没有的字段不伪造，来源没提供、不可访问、不适用、未请求和解析失败必须保存不同缺失原因。
- 商品、SKU、店铺、工商公司和厂家角色分别建模。店铺不默认等于厂家，跨平台疑似同款和疑似同一公司只建立带证据、置信度和复核状态的候选关系。
- 对商品和厂家属性采用有值才展示的原则；展示层可以隐藏缺失字段，但 L0-L2 不能删除原值、证据、缺失原因和历史变化。
- 1688 等平台的丰富厂家属性可进入扩展属性；淘宝等平台厂家字段较少不视为异常。各平台质量门禁按已验证能力分别设置。
- 京东等来源的资质入口遇到滑动验证时按总纲第 2 节采集策略自动处理或进入人工门禁，不把受限结果写成空成功。
- 分类清单附录用于采集范围、平台类目映射、平台专用关键词和分类候选；无法判定使用 `review_required`，不能直接塞入 A14。

## 产品数据完整性共识

`docs/requirements/游艺圈历史总体需求.md`（原 `project-split/04_数据采集与治理方案.md` 分册）是早期原始需求参考，其中产品字段描述偏粗，不代表后续产品数据只需要名称、分类、图片等少量字段。

游艺圈的数据核心是可搜索、可比较、可询价、可补全、可追溯的产品资产。数据来源分为两类：

1. 行业店铺（漫立方等）：通过邀请入驻获取数据 API，同步全部商品数据，作为正式产品主数据。
2. 大平台公开来源（1688、淘宝、京东、拼多多、抖音等）：通过爬虫全量采集，作为全网商品搬运库的核心来源。

产品数据应包含：

- 商品名称
- 分类
- 品牌
- 型号
- 厂家、店铺或供应商
- 来源平台、来源链接、来源商品 ID
- SKU、规格项、规格值、颜色、套餐、SKU 图片
- 价格、价格区间、批发阶梯价、促销价
- 库存、供货状态、销量或热度
- 图片、详情图、视频、说明书、画册
- 参数信息，例如控制系统、支付方式、主题风格、适用场景、适用年龄段、设备种类、尺寸、材质、电压、功率、接口、功能说明
- 适配机型
- 发货地、物流、交期
- 售后规则、质保、供应商信用
- 采集时间、更新时间、更新记录、可信度、复核状态

价格、库存、销量、供货状态属于会变化的快照型信息，不应只覆盖保存一个固定值。后续入库设计应保留采集时间和历史变化，便于判断价格走势、库存变化和来源可靠性。

SKU 不应被简化成一个文本字段。一个产品可以有多个 SKU，每个 SKU 可能对应不同规格、颜色、套餐、价格、库存和图片。采集时即使暂时无法完全标准化，也应尽量保留外部平台原始 SKU 结构和规格文本，后续再清洗映射。

## 2026-08-05 已确认决策

### 职责边界

- 游艺圈整个项目只由数据侧负责**数据获取 → 清洗治理 → 导入数据库**：包括爬虫、抓包、授权 API、文件接收等获取方式，以及去重、分类、质量门禁和入库工作流。
- 数据侧**不负责**：小程序/APP/Web 后台、交易与订单、支付、审核发布、正式业务表设计或迁移、平台运营功能。任何向"干平台项目"方向的扩展（如做后台功能、写业务接口）都不属于本工作区。
- 最终交付形态：按数据库确定字段写入接收区（`staging_manufacturer` 等），由平台校验、审核后进入正式表；数据侧不直写正式业务表。

### 初版范围与字段基准

- 初版以**现有 PostgreSQL 数据库（`192.168.1.98:5432`，schema `public`）的真实表字段**为工作流搭建基准，字段清单固化于 `docs/数据字段规范.md`。目前字段较为齐全，先按此搭建，不等待新契约。（注：正式库地址已于 2026-08-14 实测更正为 `192.168.1.43`，见当日定案。）
- 核心入库表：`staging_manufacturer`（厂家接收区，数据侧唯一直接写入点）；`manufacturer`、`product`、`accessory`、`category`、`document` 为平台正式表，只作为消费字段参考。（注：2026-08-14 实测平台未启用 `staging_manufacturer`，厂家改经 `manufacturer.import_batch` 直导，商品经 `industry_source_1688_*` 接收表，见当日定案。）
- `product` 的 `manufacturer_id` 必填：产品入库前必须先入库厂家并拿到厂家 ID/关联键，工作流按「厂家 → 产品 → 配件」顺序设计。
- `product`、`accessory` 暂无 staging 对应表，初版经平台确认前不直写正式表，先以 L3 文件或约定接口交付。
- 1688 已通过测试获取部分厂家和产品信息，作为初版主来源；采集字段按数据库字段映射，未在表中落地的来源字段（成立年份、厂房面积、资质认证、服务能力等）继续保存在 L1-L2，等待平台扩展列或正式模板。
- 历史 `游艺圈数据导入字段规范_v2.md` 已合并入 `docs/数据字段规范.md`（2026-08-05），不再单独维护；字段以真实采集与表结构映射为准。

### 采集策略

- 数据侧采集范围不做自设限制；除大平台商品信息外，按业务需要可采集授权/内测群聊、朋友圈等来源信息，新来源按需扩展。
- 为完成数据采集，允许采取一切必要技术手段降低或解除来源风控影响，包括但不限于：拟人化行为、浏览器指纹伪装、无痕/隐身环境、代理与 IP 轮换、自动处理验证码或滑块、跟随接口签名等。
- 验证码、滑块、登录失效、403/429、权限或签名要求不再视为"停止并禁止处理"；优先自动处理，自动处理无效时转人工或降频，并保留状态与证据。
- 质量与数据完整性门禁不变：不得把受限页面写成空成功，不得伪造数据，受限或局部扫描不产生下架结论。
