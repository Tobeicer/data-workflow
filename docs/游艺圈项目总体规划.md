# 游艺圈项目总体规划

版本：V1.0  
日期：2026-08-05（文档收敛）

定位：**项目级规划总文档**。说明游艺圈整个项目"是什么、分几部分、当前执行哪部分、我们只做什么"。执行细节、任务状态和下一执行点不在这里，统一在 `docs/游艺圈数据工作流总纲.md`。

## 1. 项目定位

游艺圈是面向游戏游艺行业的 **AI 数据引擎平台**（信息供应平台，不是商城）：把行业中分散、混乱、真假难辨的信息整理成可搜索、可验证、可推荐、可询价、可决策的数据资产。目标用户包括采购用户、电玩城经营者、厂家、业务员、周边服务商和行业内容生产者。

项目由两大部分组成：

| 部分 | 内容 | 执行归属 | 当前状态 |
|---|---|---|---|
| **数据侧（主线）** | 数据获取（爬虫/抓包/授权 API/文件）→ 清洗治理 → 导入数据库 | 本工作区（仓库根目录） | **当前唯一执行范围** |
| 平台侧（背景） | 小程序/APP/Web 后台、AI 识图选品、商机撮合、厂家微官网、配件商城、圈子社区、交易收费等 | 平台负责人 | 本工作区不执行，仅历史规划背景 |

## 1.1 数据侧项目目标

数据侧的目标是在来源可访问范围内，建立**可搜索、可比较、可询价、可追溯**的行业数据资产，并最终按数据库字段导入接收区：

1. **全量信息镜像**：持续采集游戏游艺设备、配件、耗材的商品、SKU、价格、供货状态、店铺、公司、厂家、资质和工厂能力信息，覆盖 1688、淘宝、京东、拼多多、抖音、闲鱼与漫立方。
2. **厂家/产品/配件分层建模**：厂家、店铺、公司、产品、SKU、配件分别建模并保留关系与证据；`shop ≠ company ≠ manufacturer`。
3. **可追溯与可信**：L0 原始证据（页面/接口/哈希）→ L1 标准化 → L2 关系、冲突、质量与复核；来源披露不等于游艺圈认证。
4. **字段全量拿到**：以 `docs/数据字段规范.md` 为准全量采集（1688 已实现厂家 73 展平字段 + 公司资产 15 个结构区块、产品 71 交付列 + 47 原始属性键、SKU 8 字段），平台表未落地字段保留在 L1-L2；**平台最终渲染/展示什么由平台决定，数据侧不裁剪字段**。
5. **入库交付**：厂家数据写入 `staging_manufacturer` 接收区；产品/配件在平台确认 staging 表或接收契约前以 L3 文件/接口交付；数据侧不直写正式业务表。

## 2. 职责边界（防跑偏红线）

### 数据侧负责（本工作区）

- 来源发现、能力评估与采集边界确认。
- 大平台爬虫（1688、淘宝、京东、拼多多、抖音、闲鱼）、邀约商户授权 API（漫立方等）、文件接收。
- 清洗、去重、分类候选、AI 辅助分析、质量门禁与复核队列。
- 可追溯的 L0-L2 资产（原始证据 → 标准化 → 关系/质量/变化）。
- 按数据字段规范（`docs/数据字段规范.md`）生成 L3 交付并写入接收区（`staging_manufacturer` 等），由平台校验后进入正式表。

### 数据侧不负责

- 小程序、APP、Web 管理后台、交易与订单、支付、担保。
- 正式业务表设计、迁移、直接写入 `public.product` / `public.accessory` / `public.manufacturer` 等。
- 平台审核、发布、上架、运营、推广、客服。
- 潜在会员库运营、营销触达（仅历史背景，不作为数据侧任务）。

## 3. 当前执行主线：数据侧（data-workflow）

### 3.1 数据资产主线

```text
来源获取（独立 adapter）→ L0 原始证据 → L1 标准化 → L2 关系/质量/复核
→ 质量门禁 → L3 交付（staging 接收区 / 契约文件）→ 平台校验审核 → 正式表
```

分层定义、运行目录、状态契约和验收规则以 `docs/游艺圈数据工作流总纲.md` 为准。

### 3.2 来源范围

| 来源 | 方式 | 定位 |
|---|---|---|
| 漫立方 | 邀约入驻授权 API/文件 | 正式产品主数据参考 |
| 1688 | 爬虫 | P0 核心来源（初版主来源，已取到部分厂家/产品） |
| 淘宝 | 爬虫 | P0 核心来源 |
| 京东、拼多多、抖音、闲鱼 | 爬虫 | P0 核心来源（待实现） |

来源状态与启用值只读 `orchestration/n8n/configs/source_registry.json`；来源细节只读对应 `adapters/<source>/README.md`。

### 3.3 数据库对接（初版字段基准）

- 字段契约 = 1688 实际采集全量字段 + 现有 PostgreSQL（`192.168.1.98:5432`，schema `public`）表结构映射，唯一维护于 `docs/数据字段规范.md`（2026-08-05 已合并历史 v2 规范与字段基准）。
- 数据侧唯一直接写入点：`staging_manufacturer`（厂家接收区）；`product`、`accessory` 尚无 staging 表，平台确认前不直写。

### 3.4 当前进度摘要

- 已确认设计（R0）与部署拓扑核验（A1）；1688 工厂面积/厂房面积拆分（D1）；数据侧职责与初版字段基准（R1）。
- 字段契约已按 1688 全量采集证据固化（2026-08-05，R2，2026-08-06 产品字段全量化）：厂家 73 / 产品 71 交付列 + 47 原始属性键 / SKU 8 字段，历史 v2 规范与字段基准已合并为单一 `docs/数据字段规范.md`。
- 1688 纵向闭环进行中：工厂档案、主体资质证据链已补齐，**阻断项为在线批次稳定性验证**。
- 详细状态、任务依赖和下一执行点只读 `docs/游艺圈数据工作流总纲.md` 第 22 节，不在此重复。

### 3.5 实现规划（阶段划分）

```text
阶段 0（当前）：1688 纵向闭环 ── 统一阶段/checkpoint/run result，在线批次稳定验证（D2）
      ↓
阶段 1：契约与运行基础（A2-A6）── 严格 Schema 验证、运行控制/逻辑数据集契约、shared 运行内核、仓库门禁
      ↓
阶段 2：n8n 控制面（B1-B6）── 需 n8n 实例落地（当前未安装）；配置、锁、路由、门禁、Master 工作流
      ↓
阶段 3：来源稳定化 ── 漫立方（C）、淘宝（E）、京东/拼多多/抖音/闲鱼（F）
      ↓
阶段 4：跨来源治理与启用（G）── 分类规则工程化、跨来源匹配、平台接收契约、逐来源启用与 30 天验收
```

- G1（分类规则工程化）是跨来源前置门禁，在 A4 完成后立即执行，不等待新平台。
- 当前执行点、任务依赖、验收与下一命令只以总纲第 22 节为准；本规划只给阶段方向。

## 4. 文档导航（AI 阅读指引）

读文档时按以下顺序，**避免把历史平台规划当成执行任务**：

1. 本文件（项目级规划：项目是什么、我们只做什么）。
2. `docs/游艺圈数据工作流总纲.md`（唯一执行基线：边界、架构、任务、进度、下一执行点）。
3. `docs/数据字段规范.md`（唯一字段契约：采集全量字段、入库映射与写库边界）。
4. 当前来源的 `adapters/<source>/README.md`（来源能力、命令、证据）。
5. `docs/游艺圈游戏游艺设备完整分类清单.md`（分类、平台类目映射、关键词）。
6. `docs/requirements/信息整理.md`（新增确认需求唯一入口）。
7. `docs/requirements/游艺圈历史总体需求.md`（历史总体需求合并档，**仅追溯背景**）。

历史需求中的"商城、支付、交易、小程序、APP、后台、潜客营销、正式写库"等内容**不自动构成数据侧执行范围**；是否执行以总纲为准。
